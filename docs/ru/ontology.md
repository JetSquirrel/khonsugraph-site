# Онтология

Метки графа говорят, откуда пришли записи: `Host`, `EntraUser`, `WazuhAgent`. Онтология говорит, что это такое: `Device`, `Account`. С ней вопрос задаётся одними и теми же словами, из каких бы источников ни был построен граф, а вы или ИИ-агент можете узнать, способен ли граф на него ответить, ещё до того, как писать запрос.

::: info В следующем выпуске
Команды онтологии, `--semantic` и `--validate-only` появятся в выпуске после 0.3.0.
:::

Онтология хранится в файлах и никогда не записывается в граф. Граф содержит то, что записали его источники данных, а [`khonsu graph rebuild`](./troubleshooting#old-format) строит его из них заново, поэтому всё, что хранилось бы только в графе, было бы потеряно.

## Понятия и сопоставления {#files}

**Файл онтологии** (`*.ontology.json`) объявляет понятия и допустимые связи между ними:

```json
{
  "format": "khonsu-ontology",
  "version": 1,
  "id": "attack",
  "revision": "0.1.0",
  "concepts": [
    { "name": "Technique", "description": "An ATT&CK technique.", "synonyms": ["ttp"] }
  ],
  "relationships": [
    { "name": "indicates", "from": "Entity", "to": "Technique" }
  ]
}
```

Понятие может расширять (`extends`) другие, а связь действует для всего, что расширяет её концы: `holds` от `Agent` к `Account` соединяет и `Person` с `Account`.

**Файл сопоставления** (`*.mapping.json`) говорит, что означают метки и типы связей графа:

```json
{
  "format": "khonsu-mapping",
  "version": 1,
  "id": "security-example",
  "revision": "1",
  "status": "draft",
  "labels": [{ "label": "Host", "concept": "Device" }],
  "relationship_types": [{ "type": "RAN_ON", "relationship": "runs_on" }]
}
```

Всё остаётся `draft`, пока человек не проверит это и не поставит `"status": "certified"`. Ответы перечисляют в `drafts` черновики, на которые опираются.

## Откуда берётся библиотека {#library}

В таком порядке; из копий одного ID побеждает первая:

1. **Встроенная**: около двадцати понятий, общих для любого расследования, например `Person`, `Organization`, `Account`, `Device`, `Process`, `IPAddress`, `Domain`, `Event` и `Observation`, и связи между ними.
2. `ontology/` в папке настроек KhonsuGraph.
3. `ontology/` в папке каждого установленного плагина, чтобы плагин поставлял смысл меток, которые он пишет.
4. Каждый переданный `--ontology PATH` — файл или папка.

Файл, который нельзя использовать, указывается в `problems` и пропускается; остальные загружаются. В примере по безопасности в репозитории есть [пакет ATT&CK и сопоставление](https://github.com/JetSquirrel/KhonsuGraph/tree/main/examples/security/ontology).

## Спросите до запроса {#commands}

```sh
khonsu graph ontology describe --db graphs/sec            # что сопоставлено, а что нет
khonsu graph ontology resolve machine login ip            # что значат слова
khonsu graph ontology check --db graphs/sec --entities account,device,ip
khonsu graph ontology path --from Account --to Device --db graphs/sec
```

- **describe** перечисляет понятия и связи, а с `--concept` показывает одно понятие полностью. С `--db` сравнивает библиотеку с графом: сопоставленные метки (с количеством), несопоставленные метки и типы связей, а также метки, которые сопоставлены, но отсутствуют в графе.
- **resolve** говорит, что значит каждое слово: понятие или связь по имени или синониму либо метка, которой сопоставление придаёт смысл. Для слова без смысла приводятся `suggestions`.
- **check** говорит, есть ли в графе записи о каждом предмете вопроса. Термин попадает в `missing` как `unknown_term`, `no_mapping` или `not_in_graph`, и тогда команда завершается с кодом **3** и видом `not_investigable`.
- **path** даёт пути с наименьшим числом шагов от одного понятия к другому: по объявленным связям и, с `--db`, по шаблонам, которые действительно есть в графе, — каждый в виде Cypher-`pattern`, готового для `MATCH`. Путь показывает, как связаны данные, а не доказывает, что вдоль него что-то произошло.

Каждый ответ содержит `ontology_versions`: использованные файлы с ID, ревизией и источником.

## Запросы словами онтологии {#semantic}

```sh
khonsu query --db graphs/sec --semantic --cypher \
  "MATCH (t:Technique)<-[:indicates]-(p:Process)-[:runs_on]->(d:Device) RETURN t.name, d.name"
```

С `--semantic` понятие, использованное как метка, заменяется всеми метками этого графа, сопоставленными с ним или с тем, что его расширяет, а связь — сопоставленными с ней типами: `(d:Device)` становится `(d:Host:Server)`, а `[:runs_on]` — `[:EXEC_ON|RAN_ON]`. Метки, которые в графе уже есть, остаются как написаны. Понятие, которому в графе ничего не соответствует, завершается с кодом 3, а не возвращает пустой результат. В результате есть `semantic`: выполненный запрос, каждая замена и использованные черновики. Семантический запрос только читает.

## Проверка запроса без выполнения {#validate}

```sh
khonsu query --db graphs/sec --validate-only --cypher "MATCH (h:Host)-[:RAN_ON]->(p:Process) RETURN p"
```

`--validate-only` проверяет запрос по графу и ничего не выполняет; `--semantic` выполняет ту же проверку перед каждым запросом.

| Вид | Серьёзность | Что означает |
| --- | --- | --- |
| `unknown_label`, `unknown_type` | ошибка | В графе нет такой метки или типа связи; в `suggestions` есть похожие имена |
| `wrong_direction` | ошибка | В графе этот шаблон есть только в обратном направлении |
| `no_such_pattern` | ошибка | В графе нет этого шаблона ни в одном направлении |
| `unbounded` | предупреждение | Шаблон переменной длины без верхней границы |
| `cartesian` | предупреждение | Части одного `MATCH` не имеют общих переменных, поэтому возвращаются все пары их строк |

Ошибка завершается с кодом 2, видом `invalid_query` и проблемами в `error.detail`; предупреждения сообщаются, и запрос выполняется. Полный справочник — в [репозитории исходного кода](https://github.com/JetSquirrel/KhonsuGraph/blob/main/docs/ontology.md).
